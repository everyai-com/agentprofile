Profile Cloud Technical Spec

The complete Cloudflare build: every product used, the data model, the crypto, the sync protocol, and the phased implementation plan. Companion to the architecture report and launch plan.

Shape of the system: one Workers monorepo serving a remote MCP server (Agents SDK McpAgent on Durable Objects), a REST/dashboard Worker, and a background pipeline (Queues + Workflows + Cron). One Durable Object per user profile is the source of truth; D1 holds the global registry and account data; R2 holds skill bundles; Vectorize holds memory embeddings; Workers AI does embeddings and skill scanning. The same codebase deploys two ways: multi-tenant cloud, or single-tenant into a user's own account via a Deploy-to-Cloudflare button.

2 · Topology & request flow

agent tool (Claude Code / Cursor / Codex) │ Streamable HTTP (mcp.profilecloud.dev/mcp) ▼ edge Worker ── workers-oauth-provider (token check, client identity) │ idFromName(userId) ▼ ProfileDO (McpAgent) ─── per-profile SQLite: grants, facts, audit, cursors ├── R2 skill bundles (read-through KV cache) ├── D1 registry + account metadata ├── Vectorize recall() semantic search ├── Queues → embed / render / scan consumers └── WebSocket broadcast → other connected clients (live sync)
  • Routing: mcp.* → MCP Worker; api.* → REST Worker; app.* → dashboard (static assets + API proxy); registry.* → public skill registry (cacheable, KV-backed).
  • Every MCP session is pinned to one ProfileDO via idFromName(userId) — strong consistency for grants and audit without cross-region coordination. Smart Placement left off (DO is the state anchor).
  • Streaming end-to-end: never buffer responses (Workers 100s/524 ceiling); MCP transport is Streamable HTTP only, no SSE legacy.

3 · Identity, auth, grants

Account

Dashboard signup via GitHub/Google OAuth (Turnstile-gated). Row in D1 accounts; ProfileDO created lazily on first use.

Client connect

Agent tool adds the MCP URL → workers-oauth-provider runs the OAuth flow (dynamic client registration) → consent screen shows requested scopes → tool receives its own access/refresh token pair. Each tool = one grant.

Grant model

Grant = {client_id, label ("Cursor · laptop"), scopes, asset filters, created, last_seen}. Scopes: skills:read, memory:read, memory:write, secrets:read (default-deny), profile:admin (dashboard/CLI only). Asset filters narrow further: skill tags, memory scopes (work/personal/dev), named credentials.

Enforcement

Every MCP tool call resolves the grant inside the DO before touching data; every allow/deny lands in the audit table. Revoke in dashboard → DO closes that client's WebSocket and rejects its token instantly (no cache-TTL lag).

4 · ProfileDO data model

-- inside each ProfileDO (SQLite via this.sql)
CREATE TABLE grants   (client_id TEXT PRIMARY KEY, label TEXT, scopes TEXT,
                       filters TEXT, created INTEGER, last_seen INTEGER, revoked INTEGER);
CREATE TABLE facts    (id TEXT PRIMARY KEY, body TEXT, scope TEXT,
                       source_client TEXT, created INTEGER, updated INTEGER,
                       superseded_by TEXT, embedding_status TEXT);
CREATE TABLE skills   (slug TEXT, version TEXT, r2_key TEXT, tags TEXT,
                       enabled INTEGER, installed INTEGER, PRIMARY KEY (slug, version));
CREATE TABLE secrets  (name TEXT PRIMARY KEY, ciphertext BLOB, wrapped_dek BLOB,
                       algo TEXT, created INTEGER, rotated INTEGER, meta TEXT);
CREATE TABLE audit    (ts INTEGER, client_id TEXT, action TEXT, target TEXT, allowed INTEGER);
CREATE TABLE cursors  (client_id TEXT PRIMARY KEY, last_sync INTEGER);
  • Memory writes: insert fact → enqueue embed job → consumer runs bge-m3 → upsert into Vectorize namespace user:<id> with metadata {fact_id, scope} → mark embedding_status=done. recall() = vector query filtered by the caller's granted scopes, hydrate bodies from SQLite, return with provenance.
  • Conflict/supersede: new fact contradicting an old one links superseded_by; nightly cron runs an LLM consolidation pass (merge duplicates, decay stale facts) inside a Workflow so it's resumable.
  • Live sync: dashboard and CLI hold WebSockets to the DO (onConnect/broadcast); a skill toggle or new fact pushes {type:"changed", kind, id} so other tools refetch on next turn.

Pluggable memory providers

Memory is a provider interface, not a hard dependency on the built-in store. Many users already live in Mem0/OpenMemory, Supermemory, or Zep — the profile should sync their memory, not force a migration. Strategically this also repositions the product: complement to the memory services (they become backends), competitor only to fragmentation.

interface MemoryProvider {
  remember(fact, scope, provenance): Promise<id>
  recall(query, scopes, limit): Promise<Fact[]>
  forget(id): Promise<void>
  health(): Promise<Status>
}
// adapters: builtin (DO SQLite + Vectorize) — default, zero-config
//           mem0        (platform API; scope → user_id/org mapping)
//           supermemory (Universal Memory API)
//           zep         (graph API; provenance from temporal edges)
  • Config per profile (dashboard/CLI): pick provider; the provider's API key is stored as an ordinary encrypted credential in the profile's own secrets table — the E2E crypto layer covers it, and the DO decorates outbound calls via the JIT path.
  • The grant/audit layer stays ours regardless of backend: per-client scope filters and audit logging wrap every recall/remember in the DO before the adapter is invoked — external providers don't have per-client access control, so this is added value, not lost value.
  • MCP surface unchanged: agents still call remember/recall; routing is invisible to clients.
  • Mirror mode (optional): writes go to the external provider and the built-in store (via Queues), so users get portability/export and can switch providers without loss. Import tooling maps Mem0/Supermemory exports into the built-in schema.
  • Caveats: external recall adds a network hop (cache hot facts in the DO with short TTL); scope filtering is emulated where a provider lacks it (tag on write, filter on read); rate limits surfaced via health() in sync_status.
  • Build order: builtin ships in P1–P2 as before; adapter interface lands in P2; Mem0 + Supermemory adapters in P4 (good community-contribution surface — one adapter per PR).

5 · Crypto design (zero-knowledge secrets)

Keys

On account creation the client (CLI or dashboard WebCrypto) derives a master key from a passphrase (Argon2id) or generates a random 256-bit key stored in the OS keychain, with a printable recovery code. The master key never leaves the device.

Per-secret

Each credential gets a fresh DEK (AES-256-GCM). Secret is encrypted with the DEK; the DEK is wrapped with the master key. Server stores {ciphertext, wrapped_dek} — both opaque to us.

Delivery

get_credential returns the two blobs to a granted client; the client-side SDK (shipped inside the CLI/MCP-client shim) unwraps and decrypts locally, injects into the tool's env just-in-time, never writes plaintext to disk. Read is audited in the DO.

Sharing (later)

Team sharing = wrap the DEK to each member's public key (X25519), so the server still never sees plaintext. This is the Bitwarden org model.

Platform KEK

A server-side KEK (in Workers Secrets/Secrets Store) adds an outer envelope on the stored blobs — defense in depth against a D1/DO storage leak, but it alone can never decrypt (client layer beneath).

6 · MCP tool surface (keep it ≤ 9 tools)

get_context()        → skills manifest + top memories for this client (one-call bootstrap)
list_skills()        → granted skills, versions, formats
get_skill(slug, format=claude|cursor|agents-md|plugin)
remember(fact, scope?)          → fact id (writes gated by memory:write)
recall(query, scope?, limit?)   → ranked facts with provenance
forget(id)
list_credentials()   → names + metadata only, never values
get_credential(name) → {ciphertext, wrapped_dek}   (secrets:read + per-name filter)
sync_status()        → cursor, pending changes, grant summary

Small surface is deliberate — big tool lists exhaust agent context windows and fail Connectors review. Skill installation, grant management, and publishing live in the REST API/CLI/dashboard, not MCP. Two lessons adopted from Executor's design: pin the serialized byte-size of tool descriptions in tests (every description byte is paid on every client turn), and keep long-form guidance behind a docs-style tool rather than in always-loaded descriptions. Where we go further: recall is semantic (Vectorize embeddings) — Executor's tool search is substring matching, so search quality is a visible edge.

6.5 · Insanely-easy onboarding

Goal: under 60 seconds from "heard about it" to a fact synced between two tools — no signup required for the first taste. Several patterns below are adapted from a deep-dive of Executor's codebase (the best onboarding in the adjacent space); the rest go beyond it.

Path A

The agent installs it. The landing page's primary CTA is a copy-paste prompt, not a command: pasted into Claude Code/Cursor, it makes the user's own agent create the profile, write the MCP config for every detected client, verify the connection, and teach a first memory. (Executor ships this "set up with your agent" prompt — near-zero engineering cost, huge win.)

Path B

One command, no login. npx profilecloud creates an anonymous instant profile: server mints an unclaimed profile whose bearer token doubles as the claim key; the CLI auto-detects installed MCP clients and writes their configs (add-mcp-style), prints the money-shot test ("now ask Cursor what you just told Claude Code"). Sign in later to claim the profile — trying it costs nothing, not even an email. Secrets features stay locked until the profile is claimed and E2E keys exist.

Path C

Web-first. Sign in at the dashboard → a two-step connect page per client with the exact command pre-filled and a copy button; connection options are encoded in the MCP URL itself as query params (e.g. ?scopes=dev,work&approval=browser) so changing behavior never needs a settings round-trip. Live checkmark flips when the client's first call lands (the DO knows instantly).

  • Kill the restart friction: most MCP clients load servers at startup. The CLI/prompt warns explicitly per client, offers to restart Claude Code itself, and the dashboard shows "waiting for first call…" so users aren't left guessing.
  • One-call bootstrap stays: get_context() returns everything a fresh client needs in a single tool call.
  • Approval UX: sensitive actions (first credential read from a new client) pause and return an approval URL; the dashboard long-polls the decision — works even in clients with no elicitation support. Default is human approval, not model self-approval (Executor defaults to the model deciding — we make the safe choice the default).
  • Self-host equally easy: idempotent deploy:setup that provisions D1/R2/Vectorize/DO, generates keys, deploys, and prints the one remaining manual step; docs list exact failure strings. Deploy-to-Cloudflare button for the click-only crowd.
  • Doctor everywhere: pc doctor checks configs, token validity, client versions, and last-call timestamps per client, and prints the fix for each failure.

7 · Skills pipeline

  1. Publish (CLI pc skill publish or dashboard): tarball → R2 staging key, row in D1.
  2. Workflow steps: validate SKILL.md frontmatter → Workers AI prompt-injection scan (flag/quarantine) → render to each client format (Cursor rules, AGENTS.md, Agent Plugins bundle) into R2 → Sigstore-sign (publisher identity from CI OIDC or account key) → flip D1 row to live → purge KV cache.
  3. Fetch: get_skill reads KV (rendered manifest) → falls through to R2. ETags + version pinning; a profile pins slug@version or tracks latest.
  4. Registry: public read-only Worker over D1 + KV, heavy Cache API usage; Turnstile + rate limits on publish; report/takedown flow writes quarantine flags that propagate to installs on next sync.

10 · Observability, limits, cost

  • Metrics (Analytics Engine, no PII): tool calls by type, sync latency, second-client connections (north star), registry installs. Dashboards via GraphQL API.
  • Logs: Workers Logs on; a Tail Worker redacts ciphertext/wrapped_dek/token fields before any sink. Never log secret values anywhere — enforced by a lint rule on the logger.
  • Design limits to respect: DO SQLite ~10GB/object (fine — one user's profile is MBs); Vectorize metadata filter on scope; Queues batch ≤ 100; Workflows for anything > 30s; Worker response streaming to stay under the 100s ceiling; R2 multipart for bundles > 100MB (rare).
  • Cost model: personal self-host ≈ free tier; cloud COGS per active user ≈ pennies/month (DO requests + duration dominate) — gross margin is a non-issue at the $12/$29 price points.

11 · Build plan (engineering phases)

P1 · wk 1–2

Skeleton that syncs. ProfileDO + McpAgent with get_context / list_skills / get_skill / remember / recall (SQLite LIKE, no vectors yet); bearer tokens; R2 skill store; CLI login + push. Demo: fact taught in Claude Code recalled in Cursor.

P2 · wk 3–4

Real auth + memory. workers-oauth-provider flow with consent screen; grants + audit; Queues + Workers AI embeddings + Vectorize recall; WebSocket live push; dashboard v1 (grants, facts, skills).

P3 · wk 4–5

Secrets. packages/crypto (client E2E), get_credential + JIT injection in CLI/SDK, audit views, KEK outer envelope. Behind a beta flag until the external audit.

P4 · wk 5–6

Self-host + registry. Deploy-to-Cloudflare template + MODE=selfhost; skill publish Workflow (validate→scan→render→sign); public registry Worker; format translators.

P5 · wk 6–8

Launch hardening. Rate limits/WAF/Turnstile; Analytics Engine dashboards; Tail Worker redaction; Connectors Directory requirements (privacy policy, docs, test account); Stripe + plan gating; load test the DO hot paths.

Grounded in the Cloudflare Agents SDK (Agent/McpAgent on Durable Objects: DO-backed SQLite via this.sql, schedule(), WebSocket onConnect/broadcast, MCP integration), Workers OAuth Provider, and current platform docs — re-verify limits and API signatures at developers.cloudflare.com during implementation. Planning only — no code written. Companions: architecture report · launch plan.
